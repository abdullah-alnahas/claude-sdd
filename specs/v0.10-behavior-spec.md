# Behavior Spec: v0.10 CC Tips Features

**Version**: 0.10
**Date**: 2026-02-03

## Overview

Testable acceptance criteria for all v0.10 features derived from Claude Code team practices.

---

## 1. Commands

### 1.1 /sdd-learn

**AC-LEARN-1**: Basic lesson capture
**Given** the user runs `/sdd-learn` after Claude made a mistake and was corrected
**When** the command executes
**Then** it analyzes the last 10 messages (or since the last lesson capture), identifies the correction, proposes a CLAUDE.md update rule, and asks "Add this to CLAUDE.md? [y/n]"

**AC-LEARN-1a**: Append-only writes
**Given** `/sdd-learn` writes to CLAUDE.md
**When** the file already exists
**Then** it appends a timestamped entry (e.g., `<!-- Learned: 2026-02-03 -->`) rather than modifying existing content, to avoid merge conflicts

**AC-LEARN-2**: Explicit lesson
**Given** the user runs `/sdd-learn "Always check for null before accessing properties"`
**When** the command executes
**Then** it uses the provided text verbatim to create a rule, without inferring from context

**AC-LEARN-3**: Notes directory
**Given** `.sdd.yaml` contains `notes_dir: notes/`
**When** `/sdd-learn` is run
**Then** it writes to `notes/lessons.md` instead of CLAUDE.md, creating the file if needed

**AC-LEARN-4**: No correction found
**Given** the user runs `/sdd-learn` but no correction is evident in recent context
**When** the command executes
**Then** it says "No recent correction found. Use `/sdd-learn 'lesson text'` to add a specific lesson."

### 1.2 /sdd-replan

**AC-REPLAN-1**: Basic replan
**Given** implementation is struggling (errors, wrong approach, complexity spiral)
**When** the user runs `/sdd-replan`
**Then** it outputs: current state summary (what works, what doesn't, what's blocked), enters plan mode, and proposes a revised approach

**AC-REPLAN-2**: Focused replan
**Given** the user runs `/sdd-replan "The caching approach isn't working"`
**When** the command executes
**Then** it focuses analysis and replanning specifically on the caching issue

**AC-REPLAN-3**: Preserve passing tests
**Given** some tests pass before replan
**When** the new plan is approved and implementation resumes
**Then** previously passing tests continue to pass (no regression)

**AC-REPLAN-3a**: Test baseline capture
**Given** `/sdd-replan` is invoked
**When** the command starts
**Then** it first runs the test suite and records which tests pass, displaying "Baseline: X tests passing" before proceeding

**AC-REPLAN-3b**: Regression warning
**Given** implementation resumes after replan
**When** a previously-passing test now fails
**Then** it immediately warns "REGRESSION: test_foo was passing before replan but now fails" and pauses for user decision

**AC-REPLAN-4**: Plan mode entry
**Given** `/sdd-replan` executes successfully
**When** the replan summary is shown
**Then** the session enters plan mode (uses EnterPlanMode tool or equivalent)

### 1.3 /sdd-techdebt

**AC-TECHDEBT-1**: Full scan
**Given** the user runs `/sdd-techdebt`
**When** the scan completes
**Then** it reports findings in categories: Duplicated Code (via pattern matching), Dead Code (unreachable exports), TODO/FIXME/HACK (comment search), Unused Imports (via grep), Long Functions (>50 lines, via line counting)

**AC-TECHDEBT-2**: Finding format
**Given** issues are found
**When** results are displayed
**Then** each finding includes: file:line, description, severity (High/Medium/Low), and code snippet preview

**AC-TECHDEBT-3**: No issues
**Given** the codebase has no detectable tech debt
**When** `/sdd-techdebt` runs
**Then** it says "No significant tech debt found. Codebase is clean."

**AC-TECHDEBT-4**: Fix mode
**Given** the user runs `/sdd-techdebt --fix`
**When** issues are found
**Then** it offers to fix each category interactively, showing proposed changes and running tests after each batch

**AC-TECHDEBT-5**: Scope limiting
**Given** the user runs `/sdd-techdebt src/components/`
**When** the scan runs
**Then** it only scans the specified directory, not the entire codebase

### 1.4 /sdd-challenge

**AC-CHALLENGE-1**: Grill mode
**Given** the user runs `/sdd-challenge grill`
**When** the command executes
**Then** it enters adversarial review mode, asking pointed questions about the changes until the user demonstrates understanding

**AC-CHALLENGE-2**: Prove mode
**Given** the user runs `/sdd-challenge prove`
**When** the command executes
**Then** it runs tests on main branch, runs tests on current branch, diffs the behavior, and explains what changed and why it's correct

**AC-CHALLENGE-2a**: Prove mode fallback (no tests)
**Given** the user runs `/sdd-challenge prove` but no test runner is configured or no tests exist
**When** the command executes
**Then** it falls back to comparing file diffs between main and current branch, explaining the behavioral implications of each change

**AC-CHALLENGE-3**: Elegant mode
**Given** the user runs `/sdd-challenge elegant`
**When** the command executes
**Then** it says "Let me reconsider this with everything I've learned..." and proposes a cleaner implementation

**AC-CHALLENGE-4**: Help
**Given** the user runs `/sdd-challenge` with no argument or `/sdd-challenge help`
**When** the command executes
**Then** it lists: grill, prove, elegant with one-line descriptions

### 1.5 /sdd-explain

**AC-EXPLAIN-1**: Default explanation
**Given** the user runs `/sdd-explain src/auth/`
**When** the command executes
**Then** it generates a text explanation of the auth module's purpose, structure, and key flows

**AC-EXPLAIN-2**: ASCII diagram
**Given** the user runs `/sdd-explain --format ascii src/api/`
**When** the command executes
**Then** it generates ASCII art showing the API structure, request flow, or architecture

**AC-EXPLAIN-3**: HTML slides
**Given** the user runs `/sdd-explain --format html src/database/`
**When** the command executes
**Then** it generates a self-contained HTML file with presentation slides explaining the database layer

**AC-EXPLAIN-4**: Concept explanation
**Given** the user runs `/sdd-explain "how authentication works in this codebase"`
**When** the command executes
**Then** it traces auth flow through the codebase and explains it step by step

## 2. Autopilot Enhancement

### 2.1 Plan-Review Step

**AC-PLANREV-1**: Critic reviews plan
**Given** autopilot completes the Design phase
**When** transitioning to Implement phase
**Then** it spawns the critic agent with prompt: "Review this plan as a staff engineer. Identify gaps, risks, overcomplexity, and missing edge cases."

**AC-PLANREV-2**: Issues found
**Given** the critic finds issues with the plan
**When** the review completes
**Then** autopilot pauses, shows findings, and asks: "Revise plan to address these issues? [y/n/skip]"

**AC-PLANREV-2a**: Max revision iterations
**Given** the plan has been revised and reviewed twice (max 2 iterations)
**When** the critic still finds issues
**Then** autopilot forces a decision: "Max plan revisions reached. Proceed with known issues or abort? [proceed/abort]"

**AC-PLANREV-3**: Clean plan
**Given** the critic finds no significant issues
**When** the review completes
**Then** autopilot outputs "Plan reviewed by critic agent - no blocking issues" and proceeds

**AC-PLANREV-4**: User skips review
**Given** the user responds "skip" to plan review
**When** the response is processed
**Then** autopilot proceeds with a warning: "Proceeding without addressing plan review findings"
