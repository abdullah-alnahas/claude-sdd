# Feature Spec: Claude Code Team Tips Integration

**Version**: 0.10
**Date**: 2026-02-03
**Source**: Boris (Claude Code creator) Twitter thread on CC team practices

## Overview

Incorporate expert Claude Code team practices into the SDD plugin. These features address gaps identified from how the CC team uses Claude differently than typical users.

---

## Feature Groups

### Group A: Learning & Adaptation (High Priority)

#### A1. `/sdd-learn` Command
Capture corrections and lessons learned, updating CLAUDE.md or project notes.

**Motivation**: "After every correction, end with: 'Update your CLAUDE.md so you don't make that mistake again.' Claude is eerily good at writing rules for itself."

#### A2. `/sdd-replan` Command
Return to plan mode when implementation struggles, preserving context.

**Motivation**: "The moment something goes sideways, switch back to plan mode and re-plan. Don't keep pushing."

### Group B: Code Quality (High Priority)

#### B1. `/sdd-techdebt` Command
Scan for duplicated code, dead code, and accumulated technical debt.

**Motivation**: "Build a /techdebt slash command and run it at the end of every session to find and kill duplicated code."

#### B2. Plan-Review Step (Autopilot Enhancement)
Add critic agent review of plans before implementation begins.

**Motivation**: "One person has one Claude write the plan, then they spin up a second Claude to review it as a staff engineer."

### Group C: Advanced Workflows (Medium Priority)

#### C1. `/sdd-challenge` Command
Prompt templates for rigorous self-review: "Grill me", "Prove this works", "Elegant solution".

**Motivation**: "Challenge Claude. Say 'Grill me on these changes and don't make a PR until I pass your test.'"

#### C2. `worktree-aware` Reference
Guidance on parallel worktree workflows with SDD context preservation.

**Motivation**: "Spin up 3-5 git worktrees at once, each running its own Claude session in parallel. It's the single biggest productivity unlock."

#### C3. `mcp-patterns` Reference
Document MCP integration patterns (Slack, databases, APIs).

**Motivation**: "Enable the Slack MCP, then paste a Slack bug thread into Claude and just say 'fix.'"

#### C4. `subagent-patterns` Reference
When and how to use subagents effectively.

**Motivation**: "Append 'use subagents' to any request where you want Claude to throw more compute at the problem."

### Group D: Extended Capabilities (Lower Priority)

#### D1. `/sdd-explain` Command
Generate explanations, ASCII diagrams, or HTML presentations.

**Motivation**: "Have Claude generate a visual HTML presentation explaining unfamiliar code."

## Acceptance Criteria by Feature

### A1. /sdd-learn

**Given** the user runs `/sdd-learn` after receiving a correction
**When** the command executes
**Then** it identifies the correction/lesson, proposes an update to CLAUDE.md (or project notes), and asks for confirmation before writing

**Given** a project has a `notes/` directory configured in `.sdd.yaml`
**When** `/sdd-learn` is run
**Then** it writes to the notes directory instead of CLAUDE.md

**Given** the user runs `/sdd-learn "specific lesson text"`
**When** the command executes
**Then** it uses the provided text directly rather than inferring from context

### A2. /sdd-replan

**Given** the user runs `/sdd-replan` during a struggling implementation
**When** the command executes
**Then** it summarizes current state (what works, what doesn't), enters plan mode, and presents a revised approach

**Given** `/sdd-replan` is run with an argument describing the problem
**When** the command executes
**Then** it focuses the re-planning on that specific problem

**Given** the re-plan produces a new approach
**When** the user approves
**Then** it returns to implementation with the new plan, preserving passing tests

### B1. /sdd-techdebt

**Given** the user runs `/sdd-techdebt`
**When** the command executes
**Then** it scans the codebase for: duplicated code blocks (>10 lines similar), dead/unreachable code, TODO/FIXME/HACK comments, unused imports/variables, overly complex functions (>50 lines or cyclomatic complexity >10)

**Given** issues are found
**When** the scan completes
**Then** it presents findings grouped by type with file:line references and severity (high/medium/low)

**Given** the user runs `/sdd-techdebt --fix`
**When** issues are found
**Then** it offers to fix each category interactively, running tests after each fix batch

### B2. Plan-Review Step (Autopilot)

**Given** autopilot completes the Design phase
**When** transitioning to Implement phase
**Then** it first spawns the critic agent to review the plan as a "staff engineer", identifying gaps, risks, and overcomplexity

**Given** the critic finds issues with the plan
**When** the review completes
**Then** autopilot presents findings and offers to revise the plan before proceeding

**Given** the plan passes review
**When** transitioning to Implement
**Then** it proceeds with increased confidence, noting "Plan reviewed by critic agent"

### C1. /sdd-challenge

**Given** the user runs `/sdd-challenge grill`
**When** the command executes
**Then** it activates adversarial review mode: "I will now grill you on these changes. You cannot create a PR until you pass."

**Given** the user runs `/sdd-challenge prove`
**When** the command executes
**Then** it diffs behavior between main and current branch, demonstrating that changes work as intended

**Given** the user runs `/sdd-challenge elegant`
**When** the command executes
**Then** it says: "Knowing everything I know now, let me scrap this and implement the elegant solution" and proposes a cleaner approach

**Given** the user runs `/sdd-challenge` with no argument
**When** the command executes
**Then** it lists available challenge modes with descriptions

### C2. worktree-aware Reference

**Given** a user reads `references/worktree-aware.md`
**When** they follow the guidance
**Then** they can set up 3-5 parallel worktrees with SDD context preserved in each, shell aliases for quick switching, and a dedicated "analysis" worktree

### C3. mcp-patterns Reference

**Given** a user reads `references/mcp-patterns.md`
**When** they follow the guidance
**Then** they can integrate Slack MCP for bug thread ingestion, database CLIs (bq, psql) for analytics, and understand when MCP vs CLI vs API is appropriate

### C4. subagent-patterns Reference

**Given** a user reads `references/subagent-patterns.md`
**When** they follow the guidance
**Then** they understand: when to append "use subagents", how subagents keep main context clean, permission routing patterns, and compute vs context tradeoffs

### D1. /sdd-explain

**Given** the user runs `/sdd-explain <path-or-concept>`
**When** the command executes
**Then** it generates an explanation in the requested format (text, ASCII diagram, or HTML presentation)

**Given** the user runs `/sdd-explain --format html <topic>`
**When** the command executes
**Then** it generates a self-contained HTML file with slides explaining the topic

**Given** the user runs `/sdd-explain --format ascii <topic>`
**When** the command executes
**Then** it generates ASCII art diagrams suitable for terminal display

## Implementation Order

1. **A1 + A2** — Learning & replan (core workflow improvements)
2. **B1 + B2** — Techdebt + plan-review (quality gates)
3. **C1** — Challenge command (advanced prompting)
4. **C2 + C3 + C4** — Reference documents (guidance)
5. **D1** — Explain command (nice-to-have)

## Stack

- Commands: Markdown files in `commands/`
- References: Markdown files in `references/`
- Autopilot modification: Edit `commands/sdd-autopilot/step-2-design.md`
- No new hooks or agents required

## Non-Goals

- Auto-learning without user confirmation (too risky)
- Automatic worktree creation (out of scope, use git directly)
- MCP server implementation (reference only, users configure themselves)
